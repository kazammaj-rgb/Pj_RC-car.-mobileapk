ARDUINO BLUETOOTH REMOTE-CONTROL RACING CAR

Android Studio + Kotlin/XML + Arduino | Case Study and Technical Documentation

This document describes the proposed architecture, hardware, wiring flow, Bluetooth command protocol, Android application, Arduino behavior, safety logic, automatic line following, test plan, and future improvements for a Bluetooth-controlled racing car.

Case study and current website are related, distinct implementations.

The case study documents a proposed Android application that communicates directly with an HC-05/HC-06. This PiRCcar website instead uses Website → Firebase Realtime Database → Python gateway → HC-06 → Arduino. The supplied firmware and physical hardware determine what actually works. The case-study single-character commands, headlights, and buzzer are proposals, not proof of supported website or firmware features.

1. Executive Summary

The Arduino Bluetooth Remote-Control Racing Car combines an Android application, Bluetooth serial communication, Arduino-based control, sensors, motor control, and basic autonomous navigation. Its purpose is to make a small racing car more interactive and extensible than a traditional physical or infrared remote.

The application supplies user controls and high-level commands. The Arduino remains responsible for real-time hardware work: reading sensors, applying motor-driver outputs, enforcing operating modes, and stopping the vehicle when required. Bluetooth carries short commands between the two layers.

The proposed functions include manual driving, ultrasonic anti-crash behavior, headlights, a buzzer, automatic black-lane following, and Bluetooth connection status. The exact hardware and pin map must be identified before the design can be treated as a build specification.

2. Case Study

2.1 Background

Many Arduino car kits are operated by a basic handheld remote, often using infrared. A smartphone interface can offer a larger control surface, clearer status, and room for additional modes without changing the core Arduino-and-motor-driver platform.

2.2 Problem Statement

A traditional remote offers limited feedback and is difficult to extend with sensor-driven behavior. The project explores whether a phone can provide convenient manual movement and select simple autonomous features over a Bluetooth serial link.

2.3 Proposed Solution

Build an Android app that pairs with an HC-05 or HC-06 Bluetooth module. The app sends short commands to an Arduino, which reads the command and controls the motor driver, ultrasonic sensor, line sensors, LEDs, and buzzer according to the selected mode.

2.4 Objectives

  • Drive forward, backward, left, right, and stop from a smartphone.
  • Provide anti-crash behavior using an ultrasonic distance sensor.
  • Switch headlight LEDs on and off.
  • Control a buzzer for a short beep.
  • Follow a physical black lane using IR line sensors.
  • Show Bluetooth connection status and report disconnection.

These are case-study objectives; headlights and buzzer are not present in the current PiRCcar hardware inventory.

3. Scope and Limitations

The initial concept assumes a typical Arduino racing-car kit: Arduino-compatible board, H-bridge motor driver, DC gear motors, Bluetooth Classic serial module, ultrasonic range sensor, and an IR line-sensor module. Kit vendors vary their boards, pin labels, electrical levels, and sensor polarity. Identify and verify the actual components and pin assignments before wiring or uploading firmware.

Line following means tracking a physical black guide lane on a prepared surface. It is not computer vision, mapping, or autonomous navigation of arbitrary roads. The 0/1 readings shown later are illustrative; sensor polarity depends on the module and calibration.

The Android design below is proposed documentation. The current website implementation is not an Android app and uses a Firebase/Python gateway path. The website’s live behavior must be assessed from its current frontend, gateway, firmware, and actual hardware, not inferred from this proposal.

Non-functional requirements

  • Controls should be understandable and usable on a phone.
  • Bluetooth commands should be short and reliably framed.
  • The vehicle should start stopped and should stop on control loss.
  • Manual, anti-crash, and auto-drive modes must be coordinated, not run as competing controllers.
  • Application and firmware responsibilities should be modular.
  • Bluetooth disconnection must not leave the motors running indefinitely.

5. High-Level Architecture

Android Phone→Bluetooth→HC-05 / HC-06→Arduino→Motor Driver→DC Motors

Android application

Provides the user interface, Bluetooth connection controls, and high-level requests such as Forward or Auto-drive.

Bluetooth serial link

Transports short command text between the phone and the paired module. HC-05/HC-06 uses Bluetooth Classic SPP, not BLE.

Arduino controller

Validates requests, reads sensors, applies mode and safety decisions, and drives the interface signals.

Power and actuators

The motor driver switches motor current from the motor supply; Arduino GPIO must not power DC motors directly.

The ultrasonic sensor, IR line sensors, LEDs, and buzzer connect to Arduino I/O and power as required by their modules. They are not connected directly to the Android phone.

Current PiRCcar web path: Website → Firebase Realtime Database → Python gateway on a Bluetooth-capable computer → HC-06 → Arduino. Firebase Hosting serves static files; it does not run the Bluetooth gateway. This differs from the proposed direct Android-to-HC-06 link.

Compatibility with current PiRCcar: its documented website/firmware protocol uses framed commands such as %F#, %B#, %L#, %R#, %S#, %T#, and %A#, plus safety/lease frames. The proposed lowercase off commands, headlight commands, and buzzer command are not thereby supported. Do not change the working framed protocol merely to match this case-study table.

10. Manual Driving Logic

  1. User presses Forward.
  2. Application sends the movement command.
  3. Arduino receives and validates the command.
  4. Arduino checks the active mode and applicable safety rules.
  5. The motor driver operates the motors if movement is permitted.
  6. Releasing the movement button requests Stop.

Actual continuous movement depends on firmware timing. A design may use a press-and-hold lease refreshed while input remains active, or a bounded movement request; in either case, release, input cancellation, and connection loss need a safe stop behavior. A button animation alone is not evidence that a command reached the Arduino.

11. Anti-Crash Logic

The ultrasonic sensor emits a sound pulse and measures the return time. Firmware converts that duration to an estimated distance, handles timeout or invalid readings, and compares valid measurements with a configurable obstacle threshold.

An example starting threshold is 20 cm; this is illustrative, not a guaranteed safe setting. Sensor placement, speed, braking distance, surface, and measurement noise all affect the usable threshold. Test at low speed and with a physical stop available.

One possible policy is to prevent forward movement when an obstacle is closer than the threshold, while allowing reverse movement only if the safety design explicitly permits it. The policy must be consistent across manual and autonomous modes. The current website's framed protocol uses %A# for Anti-Crash enable and %S# to stop/cancel; verify actual firmware behavior separately from this proposed flow.

12. Automatic Black-Lane Driving

Three IR sensors observe the surface under the front of the car. Their combined readings estimate where the black guide lane lies relative to the chassis.

LeftCenterRightTypical response
010Lane centered: move forward.
100Lane left: steer left.
001Lane right: steer right.
111Intersection or broad dark region: apply the selected junction policy.
000Line lost: stop or perform a bounded recovery policy.

Calibration limitation: the table assumes 1 means black and 0 means white. The actual 0/1 interpretation depends on the sensor module, comparator adjustment, surface, and firmware input mode; measure and verify it before use.

14. Android Studio Application Design

The proposed mobile application uses Android Studio, Kotlin for application logic, and XML layouts for the interface. Compatible HC-05/HC-06 modules are typically controlled using Android Bluetooth Classic APIs and serial-profile sockets. Android version and target SDK determine the required runtime permissions and system prompts.

Proposed UI functions

  • Bluetooth status and connect/disconnect controls.
  • Forward, backward, left, right, and stop controls.
  • Headlight on/off.
  • Anti-crash on/off.
  • Auto-drive on/off.
  • Beep control.
  • Optional speed control and diagnostic log.

The PiRCcar website is a separate web application. It does not use Kotlin/XML and does not connect directly from the browser to HC-06 Bluetooth Classic SPP.

17. Arduino Software Architecture

Bluetooth command reader

Frames serial input and rejects malformed or unsupported requests.

Motor control functions

Translate allowed movement decisions into motor-driver direction and PWM signals.

Ultrasonic distance function

Triggers a measurement and returns either a valid range or an explicit invalid result.

Anti-crash controller

Applies the selected threshold policy to movement requests.

Line sensor reader

Reads and calibrates left, center, and right sensors.

Line-following controller

Maps sensor combinations to bounded motor actions.

Headlight controller

Controls the proposed LED output if that hardware is installed.

Buzzer controller

Controls the proposed buzzer output if that hardware is installed.

Main safety/mode controller

Coordinates manual and automatic modes, stop behavior, startup state, and communication loss.

Keeping these responsibilities modular makes individual behavior easier to test and prevents sensor, mode, and motor code from competing for control.

18. Example Pseudocode

The following is pseudocode for the proposed design, not executable Arduino source.

setup:
    initialize Bluetooth serial
    initialize motor driver, sensors, LEDs, and buzzer
    stop motors
    autoDrive = false
    antiCrash = false

loop:
    command = readBluetoothCommand()

    if command == "D": autoDrive = true
    if command == "d": autoDrive = false; stopMotors()
    if command == "A": antiCrash = true
    if command == "a": antiCrash = false; stopMotors()
    if command == "H": headlightsOn()
    if command == "h": headlightsOff()
    if command == "P": beepBriefly()

    if autoDrive:
        readings = readLineSensors()
        followBlackLane(readings)
    else if command requests manual movement:
        if antiCrash and forwardRequested and obstacleTooClose():
            stopMotors()
        else:
            applyManualMovement(command)

    if bluetoothDisconnected():
        stopMotors()

    updateHeadlightAndBuzzerOutputs()

19. Safety Design

  • Default motor state is stopped after startup.
  • Stop after Bluetooth disconnection or control timeout.
  • Never power motors directly from GPIO pins.
  • Use suitable motor power and a sound ground/reference arrangement.
  • Separate noisy motor power from sensitive logic power where practical.
  • Test with wheels lifted and the chassis secured.
  • Test anti-crash at low speed with a known obstacle and a reachable stop.
  • Provide a physical power switch or emergency disconnect.
  • Do not rely on software alone for mechanical or electrical safety.

A software STOP sent over Bluetooth is not a guaranteed physical power cutoff. These are design recommendations; they are not evidence that the physical car has passed safety testing.

21. Development Phases

  1. Identify the actual car kit, board, motor driver, sensors, power source, and module variants.
  2. Document and verify the wiring relationships and voltage requirements.
  3. Test motor-driver direction and STOP behavior with wheels raised.
  4. Pair and test the Bluetooth serial link at the configured baud rate.
  5. Add and calibrate ultrasonic and IR sensor behavior.
  6. Add optional outputs such as headlights and buzzer only if physically installed.
  7. Implement and test the Android connection and manual controls.
  8. Integrate anti-crash and automatic line following with explicit mode transitions.
  9. Test connection-loss safety, document measured behavior, and produce the final pin-by-pin build record.

22. Expected Final User Experience

The intended Android experience begins with checking Bluetooth availability, granting the required permission, selecting and connecting to the car, and showing the connection state. The user can then drive with directional controls, stop the car, enable anti-crash behavior, or place the vehicle on a calibrated black lane and enable automatic following.

Connection loss should be visible and should cause the embedded controller to stop the motors. This is the proposed user experience, not a report that the Android app or physical hardware has been tested. The current PiRCcar website presents a different web-to-Firebase-to-gateway route.

24. Conclusion

The Arduino Bluetooth racing-car concept combines Android application development with embedded-system control. The application offers a user-facing control and status layer; the Arduino performs time-sensitive sensor, motor, mode, and safety work. Before producing a final pin-by-pin schematic or asserting feature support, identify the actual kit, inspect the board and modules, verify voltage requirements, and test the complete hardware path.

Appendix B — Final Wiring Deliverable

The final build record should identify every physical connection and its purpose:

  • Arduino pin number and component pin.
  • Power and ground connections.
  • Purpose of each signal.
  • Motor-driver motor supply, logic supply, enables, and direction inputs.
  • Bluetooth TX/RX and any required logic-level adjustment.
  • Ultrasonic TRIG/ECHO.
  • Left, center, and right IR sensor outputs.
  • LED and current-limiting resistor connections, if installed.
  • Buzzer connection and any required driver, if installed.

Exact wiring depends on the actual kit, board, motor driver, sensor modules, and Bluetooth board. The relationships in this case study are not a substitute for a verified schematic or the component manufacturers' electrical limits.
